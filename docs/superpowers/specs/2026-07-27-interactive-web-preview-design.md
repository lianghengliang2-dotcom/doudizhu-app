# 斗地主网页预览交互化设计

## 目标

将 `doudizhu_app/preview.html` 从静态视觉稿完善为可直接双击运行的单文件记分应用。页面不依赖服务器或第三方库，所有操作均在浏览器中完成，并使用 `localStorage` 在刷新或重新打开页面后恢复数据。

## 范围

### 玩家与设置

- 内置五名玩家，允许在设置页修改姓名。
- 新建场次时必须选择恰好三名玩家。
- 玩家选择数量不足或超过三人时，不允许开始并显示明确提示。
- 修改后的姓名立即用于新场次和当前页面；历史记录保存当时的姓名快照。

### 场次

- 空首页可以进入新建场次。
- 开始场次后，首页显示三名玩家的总分、最近三局和记分面板。
- 可结束当前场次；结束后进入历史记录，场次数据继续保留。
- 可在已有场次期间新建场次，操作前要求确认，避免误覆盖。

### 每局记分

记分面板支持：

- 选择地主。
- 选择地主胜或地主负。
- 切换春天、蒙牌。
- 选择参与“踢”的玩家及踢/反踢状态。
- 增减炸弹数量，最小为零。
- 实时显示本局基础分或倍率结果。
- 确认记分后生成一条局记录，并同步更新三名玩家的总分。

计分逻辑以现有 Flutter 项目中的 `lib/utils/score_calculator.dart` 为准，网页预览不得另行发明一套不一致的规则。

## 页面导航

- 顶部演示标签继续保留，便于直接查看各页面。
- 应用内部按钮也必须完成真实导航：
  - 首页的历史和设置图标进入对应页面。
  - “新建场次”进入玩家选择。
  - 历史记录条目进入对应场次详情。
  - 页面提供返回入口，返回到合理的上一级页面。
- 顶部演示标签切换页面时不得破坏应用状态。

## 数据模型与持久化

浏览器状态包含：

- `players`：玩家 ID、姓名和颜色。
- `activeSession`：当前场次、参与玩家、累计分数、局记录和开始时间。
- `history`：已结束场次列表。
- `draftRound`：当前尚未确认的记分面板选择。
- `schemaVersion`：数据格式版本。

状态以单个命名空间键写入 `localStorage`。每次影响业务数据的操作完成后立即保存。页面载入时先校验数据结构；数据缺失时使用默认值，数据损坏或版本不兼容时安全回退到默认状态并提示用户，不让页面因解析异常失效。

历史场次保存玩家姓名快照，确保日后修改玩家姓名不会篡改旧记录。

## 交互与错误处理

- 可点击控件使用 `button` 或明确的可聚焦交互元素，提供 hover、active、disabled 状态。
- 禁用按钮必须说明原因，例如“请选择 3 位玩家”。
- 删除、清空、覆盖当前场次等不可逆操作必须二次确认。
- 炸弹数不能小于零；未选择地主或胜负时不能确认记分。
- 记分成功后清理本局草稿并显示短暂成功反馈。
- 修复预览页现有中文乱码，源文件统一保存为 UTF-8。

## 代码组织

仍交付一个 `preview.html`，内部按以下职责组织脚本：

1. 默认数据和状态加载。
2. 计分纯函数。
3. 持久化读写。
4. 页面渲染。
5. 事件处理和导航。

业务计算与 DOM 操作分离，使计分和持久化逻辑可以在无浏览器界面的测试中验证。

## 测试与验收

采用测试优先方式，至少覆盖：

- 初次载入得到默认状态。
- 状态保存后能够重新加载。
- 损坏的持久化数据不会导致页面崩溃。
- 新建场次只能选择三名玩家。
- 地主胜、地主负及倍率项产生正确分数，且三人分数和为零。
- 确认一局会追加记录并更新累计分。
- 结束场次会移入历史记录。
- 历史记录使用姓名快照。
- 所有主要按钮都存在对应事件或导航行为。

最终使用浏览器手工验证完整路径：

1. 新建场次并选择三人。
2. 连续记录至少两局。
3. 刷新页面，确认当前场次和分数仍在。
4. 结束场次，从历史页进入详情。
5. 修改玩家姓名，再确认旧历史姓名未变化。

## 非目标

- 不接入云端、账号或多人同步。
- 不修改 Flutter 应用的数据层。
- 不引入构建工具、框架或外部依赖。
- 不实现斗地主出牌、发牌或规则裁判功能。
